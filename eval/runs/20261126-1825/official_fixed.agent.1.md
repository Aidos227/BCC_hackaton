## 7. Итог

**Итог: начинать разработку и тестирование по документу нельзя** — 2 критичных дефектов блокируют конкретные решения (см. раздел 7).

Что невозможно решить по документу сейчас:

- F-01: Определить способ передачи параметров REST API (в теле POST-запроса или в Query-строке).
- F-02: Выбрать конкретный HTTP-статус (403 или 404) для сценария доступа к чужой карте.

**Что исправить в первую очередь:**

1. **F-01** — Противоречие способа передачи параметров REST API. Перенести описание параметров из таблицы Query-параметров в Request body для метода POST или изменить тип метода на GET.
2. **F-02** — Противоречие между заголовком статуса 403 и описанием для чужой карты. Уточнить в разделе статусов, какой именно HTTP-код (403 или 404) возвращается при попытке доступа к чужой карте.
3. **F-03** — Отсутствует спецификация метода чтения настроек. Добавить спецификацию GET-метода для реализации чтения настроек уведомлений мобильным приложением.
4. **F-04** — Не указаны критерии валидности сессии. Уточнить правило проверки сессии, например: «1. Проверить валидность Bearer-токена сессии пользователя в заголовке запроса».
5. **F-05** — Не указан источник данных для проверки принадлежности карты. Уточнить источник проверки: «2. Проверить по базе данных процессинга, что карта принадлежит авторизованному клиенту».
6. **F-06** — Не описаны правила валидации суммы и переключателя. Конкретизировать шаг: «3. Проверить, что сумма находится в диапазоне 1 000–1 000 000 тенге, а переключатель равен 0 или 1».
7. **F-07** — Не определено понятие прежнего состояния при отклонении. Уточнить формулировку: «5. При отклонении суммы сохранить неизменной действующую настройку и вернуть результат ERROR».
8. **F-08** — Раздел не заполнен (заглушка). Заполнить раздел до передачи в разработку или явно указать, что он не требуется.
9. **F-09** — Чек-лист ревью не заполнен. Провести ревью и проставить отметки (агент предлагает заполнение в разделе «Чек-лист банка»).
