**Главное (критичные дефекты):**

- **F-01** — Противоречие между POST-методом, пустым телом и передачей параметров в query (строка 104; строки 147–148). Нельзя решить: Выбор архитектурного стиля передачи параметров для POST-метода: использование Query-параметров при пустом теле либо перенос параметров в Request Body формата JSON.
- **F-02** — Противоречие между кодом статуса 403 и описанием для чужой карты (строка 175; строка 189). Нельзя решить: Определение корректного HTTP-статуса для попытки изменения настроек чужой карты: возвращать 403 Forbidden или 404 Not Found.

### Замечания по отдельным требованиям

**F-04 · СУЩЕСТВЕННО · Однозначность** — Не определено событие-источник для отсчета времени  
Требования: R-13; найдено: проверка требования
- Цитата (строка 46): «Сервис передаёт push на отправку в течение минуты после получения события.»
- Проблема: Не указано, какое именно событие является отправной точкой (получение события от процессинга о покупке или событие внутренней логики сервиса), что допускает разные трактовки при разработке и тестировании.

### Замечания по набору

**F-01 · КРИТИЧНО · Непротиворечивость набора** — Противоречие между POST-методом, пустым телом и передачей параметров в query  
Требования: R-20, R-34; найдено: проверка набора
- Цитата (строка 104): «\| REST type \| POST \|»
- Цитата (строки 147–148): «* **Content-Type:** `application/json` . * Тело не используется.»
- Проблема: В документации указан тип запроса POST, однако явно зафиксировано, что тело не используется, а параметры (`cardId`, `amount`, `enabled`) описаны в секции Query-параметров и в примере cURL передаются через строку URL. Это делает невозможным выбор стандартного архитектурного решения для реализации API.
- Какое решение нельзя принять: Выбор архитектурного стиля передачи параметров для POST-метода: использование Query-параметров при пустом теле либо перенос параметров в Request Body формата JSON.
- Как исправить: Перенести параметры из query в Request body либо изменить REST type на GET.
- Вопрос владельцу: Требуется ли использовать тело запроса для передачи параметров `cardId`, `amount`, `enabled` в формате JSON при REST type POST?

**F-02 · КРИТИЧНО · Непротиворечивость набора** — Противоречие между кодом статуса 403 и описанием для чужой карты  
Требования: R-43, R-44; найдено: проверка набора
- Цитата (строка 175): «**403.** Ответ в случае, если на указанный ресурс доступ запрещен.»
- Цитата (строка 189): «Для чужой карты возвращается 404, как и для отсутствующей карты.»
- Проблема: В разделе статусов описание для 403 говорит о запрете доступа на ресурс, но в подразделе с примером ответа для 403 приводится текст про чужую карту, которая, согласно следующей строке, возвращает код 404.
- Какое решение нельзя принять: Определение корректного HTTP-статуса для попытки изменения настроек чужой карты: возвращать 403 Forbidden или 404 Not Found.
- Как исправить: Вынести описание поведения для чужой карты в отдельный блок статуса 404 или 403 без путаницы в заголовках.
- Вопрос владельцу: Какой HTTP-статус должен возвращаться при попытке обращения к чужой карте: 403 Forbidden или 404 Not Found?

## 7. Итог

**Итог: начинать разработку и тестирование по документу нельзя** — 2 критичных дефектов блокируют конкретные решения (см. раздел 7).

Что невозможно решить по документу сейчас:

- F-01: Выбор архитектурного стиля передачи параметров для POST-метода: использование Query-параметров при пустом теле либо перенос параметров в Request Body формата JSON.
- F-02: Определение корректного HTTP-статуса для попытки изменения настроек чужой карты: возвращать 403 Forbidden или 404 Not Found.

**Что исправить в первую очередь:**

1. **F-01** — Противоречие между POST-методом, пустым телом и передачей параметров в query. Перенести параметры из query в Request body либо изменить REST type на GET.
2. **F-02** — Противоречие между кодом статуса 403 и описанием для чужой карты. Вынести описание поведения для чужой карты в отдельный блок статуса 404 или 403 без путаницы в заголовках.
3. **F-03** — Документ не определяет исход: Отключенное уведомление при достижении порога расходов. Принять решение владельцем: В требованиях не описано явным образом, блокирует ли значение enabled = 0 отправку push-уведомления на уровне сервиса рассылки, хотя по смыслу признака ожидается 0 отправленных push.
4. **F-04** — Не определено событие-источник для отсчета времени. Уточнить формулировку: «Сервис передаёт push на отправку в течение минуты после получения события от карточного процессинга».
5. **F-05** — Не указаны типы данных и обязательность полей. Дополнить перечень спецификацией типов данных и ограничений для каждого поля.
6. **F-06** — Не определен механизм распознавания повторного события. Уточнить требование: «Повторная доставка события с тем же идентификатором операции сохраняет исходный итог расходов и не генерирует повторный push».
7. **F-07** — Отсутствует URL метода для продуктивной среды. Указать актуальный Production URL в таблице параметров.
8. **F-08** — Не указан алгоритм проверки суммы и переключателя. Уточнить правила валидации: сумма должна быть в диапазоне от 1 000 до 1 000 000, а переключатель равен 0 или 1.
9. **F-09** — Противоречие между Content-Type application/json и отсутствием тела. Уточнить способ передачи параметров (Query параметры или JSON body) и привести заголовок Content-Type в соответствие.
10. **F-10** — Тип данных параметра ответа противоречит описанию. Привести тип параметра amount в ответе к соответствию с запросом (integer) или явно указать строковое представление чисел.
