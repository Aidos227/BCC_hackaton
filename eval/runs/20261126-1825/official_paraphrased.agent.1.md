### Замечания по отдельным требованиям

**F-02 · КРИТИЧНО · Уместность (без лишних проектных решений)** — Использование HTTP GET для изменения данных  
Требования: R-19; найдено: проверка требования
- Цитата (строка 104): «HTTP-метод \| GET»
- Цитата (строка 108): «Request URL \| Dev: `/alerts/saveLimit` . Prod: —»
- Проблема: В документации указано сохранение настроек через метод GET («saveLimit»), что нарушает стандарты REST API, так как GET-запросы должны быть безопасными и не изменять состояние системы.
- Какое решение нельзя принять: Невозможно принять решение об использовании метода GET для операции сохранения настроек (saveLimit), так как это нарушает идемпотентность и безопасность REST API.
- Как исправить: Изменить HTTP-метод на POST или PUT.
- Вопрос владельцу: Подтверждаете ли вы использование метода GET для операции сохранения настроек вопреки стандартам REST?

**F-07 · СУЩЕСТВЕННО · Корректность** — Передача параметров изменения состояния в URL GET-запроса  
Требования: R-19; найдено: проверка требования
- Цитата (строка 104): «HTTP-метод \| GET»
- Цитата (строка 109): «CURL \| curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'»
- Проблема: Метод сохранения передает параметры изменения (`cardId`, `amount`, `enabled`) через query-параметры GET-запроса, что является антипаттерном для операций модификации.
- Как исправить: Перенести параметры в тело запроса (Request body) при смене метода на POST/PUT.

**F-08 · СУЩЕСТВЕННО · Корректность** — Указание тела для GET-метода противоречит HTTP-стандарту  
Требования: R-29; найдено: проверка требования
- Цитата (строки 147–148): «* **Content-Type:** `application/json` . * Тело не используется.»
- Проблема: В документации для GET-запроса одновременно указан заголовок Content-Type и требование отсутствия тела, что противоречит спецификации протокола HTTP для метода GET.
- Как исправить: Удалить строку с Content-Type для GET-метода, так как тело в GET-запросах не передается.
- Примечание агента: отброшено ненайденных цитат: 1

**F-09 · СУЩЕСТВЕННО · Однозначность** — Неоднозначность статусов 201 и формулировки диапазона ошибок  
Требования: R-30; найдено: проверка требования
- Цитата (строка 151): «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.»
- Проблема: Метод использует HTTP-метод GET, для которого стандарт не предполагает возврат статуса 201 Created. Формулировка «401 и далее» не определяет точный перечень обрабатываемых кодов ошибок.
- Как исправить: Исключить статус 201 из успешных ответов для GET-метода и перечислить конкретные коды ошибок вместо «и далее».
- Примечание агента: отброшено ненайденных цитат: 1

**F-10 · СУЩЕСТВЕННО · Корректность** — Тип данных полей amount и enabled в ответе не совпадает с query-параметрами  
Требования: R-31; найдено: проверка требования

## 7. Итог

**Итог: начинать разработку и тестирование по документу нельзя** — 2 критичных дефектов блокируют конкретные решения (см. раздел 7).

Что невозможно решить по документу сейчас:

- F-01: Невозможно реализовать запрос с методом GET, одновременно ожидающим Content-Type и тело.
- F-02: Невозможно принять решение об использовании метода GET для операции сохранения настроек (saveLimit), так как это нарушает идемпотентность и безопасность REST API.

**Что исправить в первую очередь:**

1. **F-01** — Противоречие между HTTP методом GET и использованием тела запроса. Изменить HTTP-метод на POST или PUT, либо полностью исключить упоминание Content-Type и тела запроса для GET-метода.
2. **F-02** — Использование HTTP GET для изменения данных. Изменить HTTP-метод на POST или PUT.
3. **F-03** — Документ не определяет исход: Ограничение частоты push: отправка второго push за календарный месяц. Принять решение владельцем: Не удалось определить бизнес-правило для сценария
4. **F-04** — Документ не определяет исход: Повторная доставка одного события процессинга. Принять решение владельцем: Не удалось определить бизнес-правило для сценария
5. **F-05** — Противоречие кодов состояния для доступа к чужой карте. Развести правила по разным статус-кодам: для чужой карты зафиксировать либо 403, либо 404 без внутренних противоречий в описании секции.
6. **F-06** — Отсутствие описания UI состояний загрузки и успеха. Дополнить раздел дизайна UI требованиями к отображению лоадера на кнопке «Сохранить» и модальному окну/тосту об успешном сохранении.
7. **F-07** — Передача параметров изменения состояния в URL GET-запроса. Перенести параметры в тело запроса (Request body) при смене метода на POST/PUT.
8. **F-08** — Указание тела для GET-метода противоречит HTTP-стандарту. Удалить строку с Content-Type для GET-метода, так как тело в GET-запросах не передается.
9. **F-09** — Неоднозначность статусов 201 и формулировки диапазона ошибок. Исключить статус 201 из успешных ответов для GET-метода и перечислить конкретные коды ошибок вместо «и далее».
10. **F-10** — Тип данных полей amount и enabled в ответе не совпадает с query-параметрами. Привести типы данных в ответе в соответствие с типами данных в запросе или явно указать сериализацию в строки.
