### Замечания по отдельным требованиям

**F-04 · СУЩЕСТВЕННО · Уместность (без лишних проектных решений)** — Использование HTTP GET для изменения данных  
Требования: R-19; найдено: проверка требования
- Цитата (строка 104): «**HTTP-метод** \| GET»
- Цитата (строка 103): «**Description** \| Сохранение порога. Функциональные требования: чтение порога»
- Проблема: Метод с описанием «Сохранение порога» использует HTTP-метод GET, хотя по стандартам REST API сохранение (изменение) состояния должно выполняться через POST, PUT или PATCH. Использование GET для модификации данных нарушает архитектурные принципы и может привести к проблемам кэширования и безопасности.
- Как исправить: Изменить HTTP-метод с GET на POST (соответственно обновив пример CURL в документации).
- Вопрос владельцу: Подтверждаете ли вы использование HTTP GET для сохранения настроек вопреки стандартам REST API?

**F-05 · СУЩЕСТВЕННО · Однозначность** — Неоднозначность шага проверки суммы и переключателя  
Требования: R-24; найдено: проверка требования
- Цитата (строка 119): «3. Проверить сумму и переключатель.»
- Проблема: Формулировка «Проверить сумму и переключатель» допускает двоякое прочтение: либо проверка наличия параметров в запросе, либо валидация их значений на соответствие бизнес-правилам (диапазон 1 000–1 000 000 для суммы и 0/1 для переключателя). Из текста непонятно, какие именно проверки и с какими код-ответами должны выполняться на этом шаге.
- Как исправить: Уточнить шаг: «3. Проверить соответствие суммы диапазону 1 000–1 000 000 тенге и допустимым значениям переключателя (0 или 1).»

**F-06 · СУЩЕСТВЕННО · Однозначность** — Не указан HTTP-статус при возврате ошибки отклонения суммы  
Требования: R-26; найдено: проверка требования
- Цитата (строка 121): «5. При отклонении суммы вернуть прежнее состояние и результат ERROR.»
- Проблема: Формулировка не определяет, какой именно HTTP-код ответа должен возвращаться при отклонении суммы — 200 с телом ошибки или статус 400.
- Как исправить: Указать конкретный HTTP-статус и структуру тела для случая отклонения суммы.
- Вопрос владельцу: Какой HTTP-статус должен возвращаться клиенту при отклонении суммы: 200 OK с телом `result: ERROR` или 400 Bad Request?

**F-07 · СУЩЕСТВЕННО · Корректность** — Противоречие в кодах ответов для статусов 401, 403, 500  
Требования: R-34; найдено: проверка требования

### Замечания по набору

**F-01 · КРИТИЧНО · Непротиворечивость набора** — Противоречие между HTTP методом GET и использованием Content-Type application/json  
Требования: R-19, R-33; найдено: проверка набора
- Цитата (строка 104): «**HTTP-метод** \| GET»
- Цитата (строки 147–148): «* **Content-Type:** `application/json` . * Тело не используется.»
- Проблема: В документации указан HTTP-метод GET для сохранения настроек, однако для него зафиксирован заголовок Content-Type со ссылкой на тело, что архитектурно несовместимо с методом GET в REST API.
- Какое решение нельзя принять: Выбор HTTP-метода для сохранения настроек (GET или POST/PUT/PATCH)
- Как исправить: Изменить HTTP-метод на POST или PUT, либо удалить требования к Content-Type для GET-запроса.
- Вопрос владельцу: Какой HTTP-метод должен использоваться для сохранения порога?

**F-02 · КРИТИЧНО · Полнота набора** — Отсутствует спецификация чтения настроек, заявленная в интеграции

**F-03 · СУЩЕСТВЕННО · Непротиворечивость набора** — Противоречие в определении успешных и неуспешных HTTP-кодов ответа  
Требования: R-34, R-35, R-36; найдено: проверка набора

- Вопрос владельцу: Должны ли ошибки валидации суммы возвращаться с HTTP статусом 400 или внутри HTTP статуса 200 с полем ERROR?
