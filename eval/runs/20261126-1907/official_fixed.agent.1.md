## 7. Итог

**Итог: разработку можно начинать с оговорками** — критичных дефектов нет, но 14 существенных нужно закрыть до приёмки.

**Что исправить в первую очередь:**

1. **F-01** — Документ не определяет исход: Изменение порога при уже накопленных расходах. Принять решение владельцем: Нужно ли отправлять push-уведомление клиенту сразу в момент снижения порога, если текущие накопленные расходы уже превышают новое значение порога?
2. **F-02** — Противоречие между описанием статусных кодов HTTP и логикой ответов API. Добавить код 404 в общую спецификацию ответов и описание статусных диапазонов.
3. **F-03** — Противоречие между использованием Query-параметров и методом POST. Перенести описание параметров `cardId`, `amount`, `enabled` из секции Query-параметров в секцию Request body для метода POST.
4. **F-04** — Отсутствие спецификации для операции чтения порога. Добавить отдельный метод GET для чтения текущих настроек порога или вынести чтение в отдельный эндпоинт.
5. **F-05** — Не описан механизм проверки сессии. Детализировать пункт: «Проверить валидность токена сессии владельца карты» или сослаться на стандарт аутентификации.
6. **F-06** — Не указан источник данных для проверки принадлежности карты. Уточнить источник данных для проверки: «Проверить по справочнику процессинга принадлежность карты клиенту».
7. **F-07** — Противоречие между методом POST и неиспользуемым телом. Изменить тип запроса на GET или перенести параметры в тело запроса (Request body).
8. **F-08** — Неоднозначность диапазона неуспешных статусов. Заменить фразу «и далее» на исчерпывающий перечень поддерживаемых кодов ошибок (например, 400, 401, 403, 404, 500).
9. **F-09** — Некорректное упоминание статуса 201 для метода сохранения. Удалить упоминание статуса 201, оставив только код 200.
10. **F-10** — Неполное описание условий появления параметров ответа. Детализировать состав полей ответа для каждого варианта значения `result` (OK и ERROR).
