### Замечания по отдельным требованиям

**F-08 · СУЩЕСТВЕННО · Однозначность** — Не указан текст и визуальный стиль сообщения об ошибке  
Требования: R-02; найдено: проверка требования
- Цитата (строка 29): «При ошибке ввода сообщение появляется под полем.»
- Проблема: В цитате не определено, какой именно текст должен выводиться при ошибке ввода и какими визуальными атрибутами (цвет, иконка) сопровождается сообщение, что допускает разную реализацию.
- Как исправить: Уточнить текст сообщения об ошибке и требования к его визуальному оформлению под полем.
- Вопрос владельцу: Какой текст и цвет шрифта должны отображаться в сообщении об ошибке ввода под полем?

**F-09 · СУЩЕСТВЕННО · Уместность (без лишних проектных решений)** — Использование GET-запроса для модификации данных  
Требования: R-19; найдено: проверка требования
- Цитата (строка 104): «HTTP-метод \| GET»
- Цитата (строка 108): «Request URL \| Dev: `/alerts/saveLimit` . Prod: —»
- Проблема: Метод называется `saveLimit` и выполняет сохранение/замену настройки, но использует HTTP-метод GET, что нарушает стандарт REST API и архитектурные принципы безопасности (модификация данных через GET не должна осуществляться).
- Как исправить: Изменить HTTP-метод с GET на POST или PUT.
- Вопрос владельцу: Подтверждаете ли вы использование HTTP метода GET для операции сохранения настроек вопреки стандартам REST?

**F-10 · СУЩЕСТВЕННО · Корректность** — Пример CURL использует параметр -G с GET методом  
Требования: R-19; найдено: проверка требования
- Цитата (строка 109): «`curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'`»
- Проблема: В примере используется флаг `-G` для CURL, который преобразует параметры в query-строку, что связано с выбором HTTP GET для операции сохранения.
- Как исправить: Изменить пример CURL на использование метода POST/PUT и тела запроса или стандартной отправки параметров.

**F-11 · СУЩЕСТВЕННО · Корректность** — Противоречие между Content-Type application/json и пустым телом  
Требования: R-30; найдено: проверка требования
- Цитата (строка 147): «* **Content-Type:** `application/json` .»
- Цитата (строка 148): «* Тело не используется.»
- Проблема: Указан заголовок Content-Type со значением application/json для метода GET, у которого тело запроса не используется, что противоречит стандартам REST API для GET-запросов с query-параметрами.
- Как исправить: Удалить требование к заголовку Content-Type для GET-запроса.

**F-12 · СУЩЕСТВЕННО · Однозначность** — Неоднозначная формулировка диапазона неуспешных статусов  
Требования: R-31; найдено: проверка требования
- Цитата (строка 151): «Если результат 400, 401 и далее — неуспешный.»
- Проблема: Конструкция «и далее» допускает два прочтения: любые коды ошибок HTTP (включая 500) или конкретно перечисленные далее в документе статусы 400, 401, 403, 500.
- Как исправить: Заменить формулировку на перечисление всех поддерживаемых кодов ошибок: 400, 401, 403, 500.

**F-13 · СУЩЕСТВЕННО · Корректность** — Несоответствие кода статуса описанию в спецификации HTTP  
Требования: R-32; найдено: проверка требования
- Цитата (строка 189): «Если карта принадлежит другому клиенту, ответ — 404, так же как при несуществующей карте.»
- Цитата (строка 175): «**403.** Ответ в случае, если на указанный ресурс доступ запрещен.»
- Проблема: В описании статус-кода 403 указано поведение с возвратом кода 404, что противоречит стандартной семантике HTTP-статусов и заголовку раздела.
- Как исправить: Перенести требование о возврате 404 в описание статус-кода 404 или изменить возвращаемый код на 403.
- Вопрос владельцу: Требуется ли возвращать именно HTTP 404 вместо HTTP 403 при попытке доступа к чужой карте для сокрытия её существования?
