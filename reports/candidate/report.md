# Отчёт о проверке требований: «Уведомление о расходах по карте»

**Итог: начинать разработку и тестирование по документу нельзя** — критичных дефектов: 3; каждый блокирует конкретное решение (см. раздел 7).

**Главное (критичные дефекты):**

- **F-01** — Критерий приёмки противоречит правилам (S2) (стр. 2, строка 13; стр. 1, строка 29). Нельзя решить: Принять решение, по какой дате (совершения или проведения) относить покупку к текущему месяцу.
- **F-02** — Правила требуют разного: Изменение порога на более высокий после уже отправленного push в текущем месяце (стр. 1, строка 32; стр. 1, строка 33; стр. 1, строки 33–34; стр. 1, строки 27–28; стр. 1, строка 29; стр. 4, строка 1). Нельзя решить: Определить бизнес-правило: разрешена ли повторная отправка push в рамках месяца при снижении или изменении порога.
- **F-03** — Правила требуют разного: Сохранение порога со значением ниже минимальной границы (999 ₸) (стр. 1, строка 27; стр. 3, строка 48; стр. 3, строка 50; стр. 4, строка 13; стр. 4, строка 30; стр. 3, строка 32; стр. 3, строка 33; стр. 3, строка 46; стр. 3, строка 52; стр. 4, строка 9; стр. 4, строка 14; стр. 4, строка 29). Нельзя решить: Утвердить единый HTTP-код (200 OK или 400 Bad Request) и структуру ответа при невалидной сумме порога.

**Уточняющие вопросы владельцу (8, полный список — раздел 8):**

- **U-01** По какому правилу относить покупку к месяцу расходов: по дате совершения покупки в Алматы или по дате её проведения? — a) По дате совершения покупки (как в Ф-2: покупка 31.01 увеличит счётчик января) / b) По дате проведения покупки (как в критерии приёмки: покупка от 31.01, проведённая 01.02, увеличит счётчик февраля)
- **U-02** Если в текущем месяце push уже отправлялся, допускается ли повторная отправка push при смене порога на новое значение? — a) Отправлять push повторно при достижении нового порога (как в Ф-4: независимо от истории предыдущей настройки) / b) Не отправлять больше одного push в месяц (как в Ф-3: максимум один такой push за календарный месяц)
- **U-03** Какой HTTP-код ответа и структуру JSON должен возвращать REST API при передаче невалидной суммы порога (меньше 1 000 ₸ или больше 1 000 000 ₸)? — a) HTTP 200 OK с телом {"result":"ERROR","message":"..."} (как в п. 5 логики метода и примере 200) / b) HTTP 400 Bad Request с телом {"message":"..."} (как в описании статуса 400)

- Доказательство (трассировка правил + вычисление модели):

```text

Ситуация: При пороге 50 000 ₸ расходы достигли 55 000 ₸, push отправлен. Клиент через API меняет порог на 80 000 ₸. Позднее проводится покупка на 30 000 ₸ (расходы 85 000 ₸).
```
