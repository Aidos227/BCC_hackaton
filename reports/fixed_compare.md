### Замечания по отдельным требованиям

**F-01 · КРИТИЧНО · Корректность** — Противоречие между указанием Content-Type и требованием не использовать тело  
Требования: R-37, R-38, R-39, R-40; найдено: проверка требования (также: проверка набора, проверка требования)
- Цитата (строка 147): «* **Content-Type:** `application/json` .»
- Цитата (строка 148): «* Тело не используется.»
- Проблема: Требования содержат прямое противоречие: с одной стороны задан заголовок Content-Type для JSON-данных, с другой стороны указано, что тело запроса не используется. При этом в CURL-примере параметры передаются через query/data-строку, что не соответствует application/json.
- Какое решение нельзя принять: Выбрать способ передачи данных в методе POST (тело JSON или query-параметры)
- Как исправить: Удалить требование о Content-Type application/json или перенести параметры из query-параметров в тело запроса.
- Вопрос владельцу: Как клиент должен передавать параметры метода POST — в теле запроса (application/json) или в query-строке URL?

**F-04 · СУЩЕСТВЕННО · Однозначность** — Неопределён механизм и критерии определения повторной доставки

В тексте не указано, по какому именно уникальному признаку (например, идентификатору операции из требований к данным) система распознает повторное событие.
- Как исправить: Уточнить механизм: «Повторная доставка события процессинга с тем же идентификатором операции не изменяет накопленный итог расходов»ционного взаимодействия.

- Цитата (строка 151): «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.»

- Как исправить: Дополнить общую логику ответов и список кодов статусов упоминанием кода 404 и исключением для кода 201, если метод возвращает только 200.

**F-14 · НЕЗНАЧИТЕЛЬНО · Понятность набора** — Типы данных в ответе API указаны как string

## 7. Итог

**Итог: начинать разработку и тестирование по документу нельзя** — 1 критичных дефектов блокируют конкретные решения (см. раздел 7).

- F-01: Выбрать способ передачи данных в методе POST (тело JSON или query-параметры)

**Что исправить в первую очередь:**

1. **F-01** — Противоречие между указанием Content-Type и требованием не использовать тело. Удалить требование о Content-Type application/json или перенести параметры из query-параметров в тело запроса.
2. **F-02** — Правила требуют разного: Покупка при выключенном уведомлении. Принять решение владельцем: Должен ли клиент получать push-уведомление при достижении порога, если для карты установлен признак enabled равный 0?
3. **F-03** — Противоречие кодов статусов HTTP и логики ответов. Дополнить общую логику ответов и список кодов статусов упоминанием кода 404 и исключением для кода 201, если метод возвращает только 200.
4. **F-04** — Неопределён механизм и критерии определения повторной доставки. Уточнить механизм: «Повторная доставка события процессинга с тем же идентификатором операции не изменяет накопленный итог расходов»ционного взаимодействия.
5. **F-05** — Не указан код ответа и формат ошибки при невалидной сессии. Уточнить шаг: "1. Проверить пользовательскую сессию; при недействительной сессии вернуть 401 Unauthorized".
6. **F-06** — Не определены критерии проверки суммы и переключателя. Уточнить шаг: "3. Проверить сумму на соответствие диапазону 1 000–1 000 000 и переключатель на значения 0 или 1".
7. **F-07** — Некорректная классификация HTTP-статуса 201 как успешного для данного метода. Исключить упоминание статуса 201 из правила успешных результатов, если метод возвращает только 200.
8. **F-08** — Конфликт описания кода 403 в тексте и заголовке. Уточнить в формулировке статус 403, описав конкретный бизнес-кейс возникновения ошибки доступа, не пересекающийся с чужой картой.
9. **F-09** — Отсутствует структура тела ответа для статуса 403. Добавить JSON-пример или описание структуры ответа для статуса 403.
10. **F-10** — Не указаны условия возникновения ошибки 403 для тест-дизайна. Конкретизировать условие возврата статуса 403 (например, отсутствие прав на уровне ролей или сервиса).
