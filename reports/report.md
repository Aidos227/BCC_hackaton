### Замечания по отдельным требованиям

**F-02 · КРИТИЧНО · Уместность (без лишних проектных решений)** — Использование метода GET для операции сохранения настроек  
Требования: R-13, R-18; найдено: проверка требования (также: проверка набора)
- Цитата (стр. 3, строка 32): «REST type GET»
- Цитата (стр. 3, строка 36): «Request URL Dev: /alerts/saveLimit . Prod: —»
- Проблема: Требование назначает HTTP-метод GET для операции сохранения/замены настроек («Сохранение порога», «Заменить настройку»), что нарушает стандарты REST API (методы GET должны быть безопасными и не изменять состояние ресурсов на сервере). Без выбора корректного метода (POST или PUT) невозможно реализовать и протестировать защищённое сохранение данных.
- Какое решение нельзя принять: Выбор HTTP-метода для сохранения настроек (GET нарушает стандарты REST API для модификации данных)
- Как исправить: Изменить тип REST-запроса с GET на POST или PUT.
- Вопрос владельцу: Согласны ли вы изменить HTTP-метод с GET на POST/PUT в соответствии с принципами REST?

**F-04 · СУЩЕСТВЕННО · Однозначность** — Не определен критерий успешной передачи push-сервису  
Требования: R-11; найдено: проверка требования
- Цитата (стр. 1, строка 39): «Сервис передаёт push на отправку в течение минуты после получения события.»
- Проблема: Требование допускает два прочтения: минута отсчитывается с момента формирования события в процессинге или с момента успешного получения/обработки этого события сервисом уведомлений. Также не указан ожидаемый результат при сетевом сбое.
- Как исправить: Уточнить точку отсчета одноминутного интервала и поведение при недоступности сервиса уведомлений.
- Вопрос владельцу: С какого именно момента (генерация в процессинге или прием сервисом) начинается отсчет одной минуты для передачи push?

**F-05 · СУЩЕСТВЕННО · Полнота** — Не указаны типы данных и обязательность для всех полей  
Требования: R-12; найдено: проверка требования
- Цитата (стр. 2, строки 2–3): «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.»
- Проблема: В требовании перечислены сущности для хранения, но полностью отсутствуют типы данных, размеры и признаки обязательности (NULL/NOT NULL) для идентификатора карты, месяца, идентификатора операции и признака отправки.
- Как исправить: Дополнить требование спецификацией типов данных, размерности и ограничений для каждого сохраняемого поля.

**F-06 · СУЩЕСТВЕННО · Однозначность** — Не определено понятие повторной доставки события процессинга  
Требования: R-14; найдено: проверка требования
- Цитата (стр. 2, строка 6): «Повторная доставка одного события процессинга сохраняет исходный итог.»
- Проблема: Формулировка допускает два прочтения: 1) дублирующее сообщение полностью игнорируется системой без изменения данных; 2) сообщение обрабатывается повторно, но идемпотентно перезаписывает те же самые данные без изменения итогового счёта. Из текста нельзя понять технический механизм обеспечения неизменности итога.
- Как исправить: Уточнить механизм обработки дубликатов: «Повторная доставка идентичного события процессинга (с тем же идентификатором операции) обрабатывается идемпотентно без изменения накопленного итога расходов»

**F-07 · СУЩЕСТВЕННО · Однозначность** — Неоднозначный формат идентификатора карты в примере и описании  
Требования: R-24; найдено: проверка требования
