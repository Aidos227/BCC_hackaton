## 7. Итог

**Итог: начинать разработку и тестирование по документу нельзя** — 2 критичных дефектов блокируют конкретные решения (см. раздел 7).

Что невозможно решить по документу сейчас:

- F-01: Невозможно однозначно реализовать и протестировать поведение для покупок на стыке месяцев по времени Алматы и дате проведения.
- F-02: Невозможно определить архитектурный стандарт передачи параметров (GET с query или POST с body) для реализации метода сохранения настроек.

**Что исправить в первую очередь:**

1. **F-01** — Критерий приёмки противоречит правилам (S2). 
2. **F-02** — Противоречие типа HTTP-метода в спецификации API. Изменить REST type на POST или PUT в соответствии с логикой сохранения настроек.
3. **F-03** — Противоречие кодов успешного ответа API. Исключить код 201 из списка успешных ответов, так как метод не создает новый ресурс с уникальным URI.
4. **F-04** — Метод сохранения использует GET вместо POST/PUT. Изменить тип метода с GET на POST или PUT.
5. **F-05** — Противоречие между описанием сохранения и типом GET. Уточнить в Description, является ли метод чтением или сохранением настройки.
6. **F-06** — Не указан URL метода сохранения для Prod контура. Указать актуальный Prod URL для метода сохранения порога.
7. **F-07** — Указан Content-Type при отсутствии тела запроса. Удалить требование о Content-Type либо уточнить, что он передается при наличии тела.
8. **F-08** — HTTP код 201 не соответствует спецификации GET-метода. Исправить код успешного ответа на 200 или изменить REST type на POST/PUT.
9. **F-09** — Неоднозначная формулировка диапазона кодов ошибок. Заменить формулировку на перечисление конкретных кодов или диапазон 400-599.
10. **F-10** — Раздел не заполнен (заглушка). Заполнить раздел до передачи в разработку или явно указать, что он не требуется.
